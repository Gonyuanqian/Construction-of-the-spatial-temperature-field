# 实时监测页面开发交接

更新日期：2026-10-18。页面：`/live`。当前已有可运行实现。

开发前先阅读[共同设计与开发约定](00-shared-ui-guidelines.md)。本文记录当前能力、已经确认的界面方向和后续建议；建议不表示必须全部开发，排期和方案可由团队结合实际使用调整。

## 1. 页面目标

用户进入页面后，应能快速看到当前展示时刻的温度空间分布，查询一个位置，理解均温和沿棚差异。页面继续以温度场画布为中心，配套信息帮助读图。

与另外两页的分工：助手接收自然语言并组织解释；历史页查询过去的记录。实时页提供当前观察对象和跳转上下文，不承担完整对话记录和历史数据表格。

## 2. 当前实现及能力边界

| 能力 | 现状 |
| --- | --- |
| 数据源 | 固定 `configs/live/train.xlsx` 与 `live.xlsx`，独立于训练页上传数据集 |
| 播放操作 | 准备、开始、暂停、下一帧；默认 300 秒一帧 |
| 状态同步 | 运行时前端每 5 秒检查服务状态，帧号改变才重取帧与摘要 |
| 场景 | 默认三维，可切断面；三维模块懒加载 |
| 查询 | 悬停、点击钉住、坐标查询；越界和无测量带有专门解释 |
| 概览 | 棚内平均温度、场景状态、更新时间 |
| 底部 | 环境参数卡片和沿棚均温曲线 |
| 工具 | 剖切、示意长度、相机控制及读数等，由三维组件投放到右栏 |
| 存储 | 运行状态在内存；尚无历史记录归档和外部设备持续接入 |

模型是否可用与实时源是否准备完成是两件事。`prepare()` 使用准备时的模型建立独立管线；已有管线时再次准备直接返回。不要假设在模型库切换选择后，已准备的实时源会自动换模型。

## 3. 已确认的布局方向

这些方向来自现有界面的用户反馈，继续开发时应作为设计基线：

1. 训练/实时模式切换位于左导航上方，把中央顶部空间留给画布。
2. 桌面主体验中，棚体三维温度场、环境参数、沿棚均温尽量完整同屏。
3. “棚体三维温度场”标题进入画布；“棚位 y …”放在左上角标题右侧；温度色标竖排在画布最右侧。
4. 环境参数内部的均温圆环、拱跨宽、拱顶高三个元素左右并排，避免重新堆成上下两层。
5. 环境参数和三维视图控制复用方框、线框图标、标签与读数的表达。
6. 沿棚均温图在现有卡片内充分利用高度；标题不重复，坐标标签清楚，底部不留大块空白。
7. 常驻首屏不增加帧号、总帧数等技术信息卡；复杂口径继续放到可展开说明或上下文细节。

建议空间组织如下，比例根据屏幕和内容调整：

```text
系统顶栏
┌ 左导航与模式 ┬ 中央观察区                    ┬ 工具区       ┐
│ 实时监测     │ 紧凑操作、视图切换和概览      │ 点选与坐标   │
│ 智能助手     │ 棚体三维温度场：主要弹性区域  │ 剖切与几何   │
│ 历史数据     │                              │ 三维控制     │
│ …            │ 环境参数     │ 沿棚均温       │              │
└──────────────┴───────────────────────────────┴──────────────┘
```

窄屏允许布局重排和必要滚动，不能通过缩到看不清、隐藏标签或裁掉内容来满足“一屏”。桌面布局的环境参数三项并排应保留；新增内容优先收进右栏、折叠区或其他页面。

## 4. 后续开发建议

| 建议方向 | 解决的问题 | 可选择的实现范围 |
| --- | --- | --- |
| 当前数据来源与状态 | 用户分不清展示时间、真实挂钟、运行状态 | 在现有概览或轻量状态标签上补充，不新增大段技术面板 |
| 帧与场景一致性 | 摘要已到新帧，但三维仍在构建旧帧 | 保留旧场时明确显示其数据时间，完成后再统一更新相关标识 |
| 更清楚的查询反馈 | 吸附后的坐标与用户输入可能不同 | 显示最近格点、时间、场值来源，突出钉住状态 |
| 助手联动 | 用户希望解释正在看的位置 | 通过“询问此位置”等入口携带当前上下文到助手页或抽屉 |
| 历史联动 | 用户想继续查看当前时间附近变化 | 带来源与时间进入历史页，目标时间不存在时说明原因 |
| 模型来源补齐 | 当前选择与管线实际使用模型可能不同 | 后端增加实际运行模型描述；如何重新准备和提示可讨论 |
| 长期数据接入 | 演示源未来可能替换为现场数据 | 抽象数据来源和状态契约，设备协议和存储方案另行评估 |

建议先完成状态准确、界面稳定和跨页上下文，再决定是否增加更多读数。高温告警、未来温度预测和设备控制尚无本页既定需求，应另行定义数据依据和流程。

## 5. 当前接口与请求关系

以下接口已经存在，路径包含 `/api` 前缀。准确参数与响应以路由和 `api/types.ts` 为准。

| 接口 | 用途 | 注意点 |
| --- | --- | --- |
| `GET /api/models` | 查询可用模型 | 不把请求失败当成模型库为空 |
| `GET /api/live/status` | 轻量读取状态 | `idle/ready`、`running`、`cursor`、`total`、`interval_s` |
| `POST /api/live/prepare` | 同步准备管线 | 可能需要几十秒；返回 `PrepareResult`，不等同于 `LiveStatus` |
| `POST /api/live/start` | 开始播放，可选 `from_n` | 改变共享实时源，其他页的回看不要调用它 |
| `POST /api/live/pause` | 暂停 | 操作完成后重新读状态 |
| `POST /api/live/next` | 前进一步 | 暂停时也有效，末帧应有清楚反馈 |
| `GET /api/live/frame/{n}` | 本帧断面、传感器与气象数据 | `n` 必须已经走到；`frame.time` 和管线时间保持一致 |
| `GET /api/live/volume/{n}` | 三维体网格或摘要 | 支持 `preset`、`monotonic`、`y_step` 和 y 范围 |

当前摘要以 `y_step=3` 取沿棚七片；三维通常以默认 0.5m 取更密的切片。两者请求应指向同一帧，但允许采用不同密度，不能为了减少请求直接把三维降为摘要分辨率。摘要均值和高分辨率全体积均值也不能未经定义就当成同一个统计量。

帧号由实时源转换成管线下标，前端不写固定的偏移量。帧与体网格请求可能触发内部管线按需补入已经走到的帧；历史页需要独立的读取能力，不能借用这些调用推进监测状态。

## 6. 状态、数据与性能要求

- 分别处理模型库加载中、无可用模型、源未准备、正在准备、正在播放、暂停、末帧、局部请求失败及场景落后。
- 请求失败时可以保留最后一次成功场，但必须显示数据时间和失败提示；旧图不能显示成“刚更新”。状态字段和读数来自响应，空值不补零。
- 当前的 `useAsync` 用请求序号避免旧响应覆盖新结果。新联动和并发逻辑继续遵循这一原则，需要时增加请求取消。
- 运行时只轻量轮询；暂停时沿用当前停止轮询策略。切页清理计时器；历史回放和问答不能额外启动一套全局实时推进器。
- 三维继续懒加载；滑块等连续操作沿用防抖，释放 WebGL 资源和监听，避免无界缓存体网格。
- 显示温度来源时复用 `pick.ts`。空间插值、统计和有效区域掩膜由后端维护；示意长度变化只改几何。
- 助手页所需的跨页选点目前没有完整外部联动契约。可以从 `VolumeView` 的局部查询状态渐进提取输入/事件，不复制一套场景组件。

## 7. 建议实施顺序与分工

1. 前端先记录当前桌面布局与关键交互基线，找出真实使用中的状态或布局问题。
2. 共用层负责人完成实时工作区路由识别和跨页上下文的初步约定。
3. 后端补齐实际数据来源、模型版本和统计设置等缺失元信息；前端接入并保持旧接口兼容。
4. 各页面负责人实现最小联动，再根据反馈决定是否加入更多环境指标或分析。

布局微调、来源信息和联动可拆开交付，不要求一次重写 `LiveView`。共享代码的拆分方式由团队按实际复用程度决定。

## 8. 建议验收

- 1920×1080 与 1440×900 下检查三块同屏和画布可读性；较窄屏幕检查标签、控件和滚动。
- 三维标题、棚位和竖向色标位置符合当前方向；底部环境三项并排，曲线无重复标题和轴文字重叠。
- 开始、暂停、下一帧、末帧、刷新、模型缺失、源未准备和断线能走通。
- 主图、断面、摘要和读数来自明确的同一帧；更新期间旧图有时间说明。
- 越界、拱外、无测量带、吸附格点和剖切后的悬停读数符合现有口径。
- 页面跳转与直接刷新保持实时主题；从助手或历史页回来不误改当前播放位置。
- 自动验证建议复用 `LiveView.test.ts`、`liveLayout.test.ts`、`VolumeView.test.ts`、`liveMeanCurve.test.ts`、外壳与实时接口测试。WebGL 相机、剖切和实际布局仍需要人工操作检查。
