# 温室方案 AI 检验

更新于 2026-11-17。对应用户工作台 `/greenhouse-design` 右侧的“AI 检验 · AgriSeek”，沿用现有三列布局。

## 用户操作

1. 编辑位置与朝向、结构与覆盖、作物与种植、滴灌与喷灌四组参数，保存草稿。
2. 点击“开始 AI 检验”。后端读取该账号已经保存的版本，建立固定快照后提交 AgriSeek；页面展示执行状态，可以取消。
3. 发布结果分别展示“检验结果”“调整建议”“待补充信息”，可展开查看依据。完成状态表示分析任务完成，不表示方案通过工程认证。
4. 修改参数或保存新版本后，旧结论显示版本提示。保存后手动重新检验；不会自动生成新任务或修改设计。
5. 刷新页面后，重新选中个人方案即可读取最新检验；最近 20 条记录可从历史列表选择。切页暂停前端轮询，服务端任务继续执行，返回时读取同一任务。

尚未保存、草稿有修改、模型未配置或记录正在加载时，不能启动检验。提交失败后的重试复用原请求编号；提交状态未确认时，不通过查询接口悄悄重新提交。完成的公开结果保存到 MySQL，计算服务离线时仍可读取已归档结果。

## 分工与数据

Spring Boot 管理拥有者、方案版本、请求幂等和结果留存；Python 复用 AgriSeek 的候选生成、资料检索、数值/引用校验及独立审核。前端只发送版本号与请求编号，不能提交另一份 spec、owner_id 或分析快照来替换服务器记录。

Flyway V10 新建 `greenhouse_design_inspection`：保存方案 ID、拥有者、修订号、不可变参数和几何摘要、请求编号、分析快照/任务编号及完成结果。旧方案和监测配置不变。所有查询按拥有者限定，管理员的个人方案也采用独立的助手命名空间。

Python 将服务端保存的四组参数转为 `F:design:*` 事实，并纳入服务端几何计算的面积、有效长度、种植带/行/株数、喷头数量和布局提示。模型不读取浏览器当前草稿，不调用温度网格或天气接口。名称不进入模型上下文；搜索服务仅接收固定的公共设计主题词，不发送项目名称、坐标等私人文本。模型服务会接收设计事实，使用现有 AgriSeek 凭据及部署配置。

当前手动喷头坐标只提供前五个样本，并明确标注范围；因此不声称完成了所有喷头的水力或覆盖分析。缺少品种、海拔、荷载、覆盖材料性能、土壤、水源或喷头水压等条件时，允许明确给出待补充项。输入参数本身是设计事实，不是现场实测。

## 接口

使用现有 Bearer 登录，前缀 `/api/user/greenhouse-designs`：

| 方法与路径 | 行为 |
| --- | --- |
| GET `/inspection-capabilities` | 查询已配置的助手能力，先核验内部协议版本 |
| POST `/{id}/inspections` | `{revision, request_key}`，仅接受已保存的本人方案；UUID 请求键防重复 |
| GET `/{id}/inspections/latest` | 最新记录 `{inspection: ...或null}`，读取运行状态或缓存结果 |
| GET `/{id}/inspections` | 本方案最近 20 条检验记录 |
| GET `/{id}/inspections/{inspectionId}` | 指定记录及其运行状态或结果 |
| POST `/{id}/inspections/{inspectionId}/cancel` | 取消同一任务；已经完成则返回归档结果 |

内部增加 `POST /internal/v1/assistant/design-snapshots`，需要内部凭据和拥有者上下文。快照 ID 由检验编号确定，同编号异内容返回 409；任务/会话编号也稳定生成，以恢复丢失的提交响应。已有内部 runs 查询、取消和审核协议继续复用。Java 要求 Python `/assistant/info` 的 `design_inspection_version` 与 `owner_isolation_version` 均为 1，必须一同升级两个后端。

## 模型输出与边界

沿用现有候选结构，各 claim 以 `【检验结果】`、`【调整建议】` 或 `【待补充】` 标识，UI 按标识分区。完整分析必须包含结果与建议，并至少引用一条本方案事实；纯通用模板不能发布。数字、事实引用和适用条件仍须通过校验和独立审核；审核失败时显示真实失败或部分结果状态。2026-11-18 起使用下述初步分析流程，不再强制设计检验重复通过两轮聊天审核。

不将“几何可生成”解释成农艺适宜或结构安全，不生成无依据的精确间距、承载能力、温控效果或设备处方。功能不修改参数、不控制设备、不替代工程计算，也不改变现有温度场模型。后续可以补充有适用范围的栽培/工程资料、完整设备覆盖分析和更多结果展示，但应保留版本绑定与证据校验。

## 初步分析流程调整（2026-11-18）

真实任务排查发现两次失败均发生在回答审核之前：一次检索循环耗尽执行预算，一次模型连接中断。活动知识库为 8 条定性温度机理资料，不包含完整的温室设计规范；不能将其覆盖范围当成模型全部可回答范围。

温室设计检验改用专门的有限步骤流程：可选检索一次现有知识（短超时，最多取三条）→依据保存方案和通用知识生成初步分析→数值/引用逐条校验→独立核验。核验只关注方案一致性、事实可靠性、建议边界和分析有用性；通过一次即可发布，失败最多定向修订一次。没有模型驱动的反复联网搜索，不修改普通问答和温度查询的规则。内部 info 增加 `design_inspection_policy=advisory-v2` 用于部署核对。

知识库未配置、检索失败或资料不匹配，不阻止模型解释设计取舍和提出定性建议。缺少荷载、材料参数、参龄或水力资料，只限制对应的具体结论。模型仍须结合至少一条本方案事实，不能以通用模板冒充检验。若个别主张的数字或引用不成立，先剔除该主张，对其余内容独立核验，通过后作为部分分析发布；不将整体任务无条件放行，也不编造安全认证或精确设备设定。

前端增加“初步方案分析”说明，并标出通用知识分析、条件性推断、方案与资料分析。返回结果继续绑定保存版本并支持取消、恢复和历史读取。旧的失败记录保留，升级后需主动点击“重新检验”，不会自动补发任务或改写历史。

验证：69 项相关 Python 回归、32 项前端回归通过，类型检查与前端构建通过；浏览器使用本地模拟模型验证单次独立核验、刷新和版本恢复。另使用不含账号、个人名称或地点的合成参数调用真实 AgriSeek，关闭知识库和联网后，最终一次在 12.88 秒内完成生成与独立核验两次模型调用，发布 7 条覆盖四组配置的初步分析与建议。此前一次合成验证未形成可发布候选，已增加不含候选正文的格式诊断。最终通过记录为 `.local/greenhouse-inspection/advisory-real-verification.json`。这是功能验证，不是农艺或工程正确性认证；知识库仍未补入新的设计规范。

## 多字段引用导致整份结果被拒绝的修复（2026-11-18）

再次排查真实任务时，新增的格式诊断明确记录了 `claims[n].evidence_ids: too_long`。温室检验复用了普通问答的“每条最多 6 个引用”限制，种植或灌溉结论涉及多个字段时容易超限。模型已经返回完整正文，却在候选解析阶段整体失败；另一次在这种失败后的重新生成请求中出现连接中断。先前成功的简单合成示例没有覆盖这个边界。

设计检验现在使用独立的候选类型，每项最多 64 个引用，足以容纳当前白名单设计字段及辅助资料；普通问答仍维持原来的 6 个限制。所有引用完整保留，不能简单截断前六条，以免遗漏数值来源。未知引用、无依据数字、推断条件及独立核验规则保持生效。格式修复反馈给出具体字段和上限，并保留不含候选正文的诊断。内部 info 增加 `design_citation_limit: 64`；结果版本为 `greenhouse-design-advisory-v2.1`。

验证包含 7、12、24 条引用的完整执行回归、64 条上限、普通问答限制不变、虚构来源和数字继续阻止，共 74 项相关 Python 回归通过。浏览器模拟结果也使用八条引用，结果显示、重新检验及历史恢复通过。

另连续运行三组合成参数的真实检验，均在一次生成和一次独立核验后给出结果：多字段综合案例 13.61 秒，5 项分析，单项最多 8 个引用；连栋示例 16.94 秒，7 项分析，单项最多 7 个引用；仅滴灌示例 11.86 秒，7 项分析，单项最多 7 个引用。三次均按 `partial` 发布通过核验的部分，包含检验结果和调整建议，个别未通过依据检查的主张被省略，没有绕过核验。记录在 `.local/greenhouse-inspection/citation-real-verification.json`；仅使用合成参数，没有提交个人方案、账号或地理坐标。

## 单次检验与 AgriSeek 对话列表分离（2026-11-20）

单次温室 AI 检验继续保存任务、版本、结果和执行事件，但不再自动进入 AgriSeek 历史对话列表。首次检验的根任务由服务端根据固定检验请求和已保存的设计快照标记 `conversation_origin=greenhouse_design_inspection`；列表只隐藏尚无追问的这类根任务。真正提交以它为父任务的追问后，会话出现在列表中，标题使用首条追问，重复提交同一请求不会生成多条会话。只读取关联会话作预览不改变显示状态。

兼容旧记录时，根据原来的固定检验问题及不可变设计快照判断来源，不删除 SQLite 或 MySQL 中的检验记录。过滤先于列表的 100 条上限，避免大量检验挤掉正常会话。普通问答、手动发起的设计问题、农事建议以及已经追问的会话继续保留；拥有者命名空间及跨账号权限保持不变。

前端在恢复本机缓存和合并服务端列表时清除单次检验，防止旧摘要重新出现。预览根任务时不将它另存为侧栏对话，发送追问后才保存，并以追问内容命名；仅缓存了追问末轮的已有会话同样保留。内部 info 提供 `inspection_history_policy=followup_only` 供部署检查。
