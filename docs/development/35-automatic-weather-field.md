# 地点选择后的自动温度场构建

更新：2026-11-09。

> 2026-11-10 实时监测只重建实况时刻。来源改为实况温湿度 + 15 分钟窗口内的近实时光照估算；未来预报场不再展示。以下为自动构场第一版交接记录，最新时间及来源要求见 [近实时气象协议](36-near-realtime-weather.md)。

## 用户流程与范围

确认地点 → 查询和风天气 → 接入层归一化温湿度、估算 lux → 服务端选择已发布模型配置 → G 预测 24 个虚拟棚内点 → 冻结的 F 构场 → 保存气象、来源与配置快照 → 大屏读取同一份三维结果。

不增加输入表单、模型选择或新的三维页面。已有地点偏好在登录账号打开页面时自动接续。原来的 5 秒状态轮询只读保存结果，不重复推理或访问收费天气源；气象到期更新才触发后续链路。失败不无限重试，用户点击气象条右侧刷新即可重新查询、获得新凭据并重试。

当前天气接口提供的是预报，棚内点是模型预测值，均不是现场实测。天气接口的 15 分钟样本不能冒充 13 条连续 5 分钟实测数据；自动链路固定走已发布包中的 `current_only` G，保留现有 F 及物理约束，不重新训练，也不补造历史。

## 接口与模型选择

`POST /api/live/weather/query` 返回 `query_id` 和 `source_fingerprint`。构场接口：

```http
POST /api/live/weather/construct
Authorization: Bearer <当前账号令牌>
Content-Type: application/json

{"query_id":"查询接口返回的 UUID"}
```

只接受此字段，不接受浏览器自行填写的天气、模型、来源或换算系数。服务端保留最长 120 秒的账号绑定查询快照；最多 4096 条，过期或不属于当前账号返回 409，需重新查询。查询缓存和构场凭据均是进程内状态，重启会清空；已保存温度场不受影响。

成功响应包含原有 WeatherFrame，以及可直接用于大屏的 `live` 状态。未配置模型、模型停用、不兼容尺寸、查询失效、计算错误均显式返回，不使用模拟温度填补。

默认复用唯一启用的棚体配置。多份启用配置时，管理员需要在服务端设置 `TFIELD_AUTOMATIC_GREENHOUSE_ID`，可写入本机 `.local/system.local.json` 的 `Environment` 并重启。该编号必须对应启用、尺寸兼容且已绑定已发布 G/F 模型的配置。不按地区挑模型，不随意选最新模型；地区仅标识气象来源。

目前模型仍只支持 `ginseng_arch_v1`，18 × 2.1 × 1.3017 m；这次改造没有增加形体缩放能力。

## 幂等、历史与地点切换

- 来源指纹包含提供商、数据类型、有效时刻、实际查询网格、气象值、光照换算方法；不包含拉取时间或缓存标记。
- 结果身份还包含账号、棚体配置与修订号、地区。同一气象与配置重试复用旧结果；同一预报有效时刻被供应商修订、改选网格或模型配置更新时分别保留新结果。
- V7 只将 `weather_frame.location_key` 从 CHAR(6) 加宽为 VARCHAR(80)，沿用唯一索引，保留既有手动气象历史。旧接口仍可用。
- 保存 `summary.weather_source` 和光照换算原始元数据；不会将已归一化的 lux 再乘一次系数。即使两输入 G 不使用外部湿度，大屏仍保存 API 的真实输入湿度，不以 G 估计值代替。
- 前端以请求代次丢弃旧地点回执，构场成功后固定保存结果编号。状态、体网格和点查询带 `session_id`；服务端只允许读取本账号已保存的自动构场，避免另一个地点晚完成而覆盖当前地点。
- 统一启动脚本检查 `weather_constructing`，有构场请求时拒绝普通停止/重启。

## 模型适用范围

新发布模型包包含 G 训练阶段记录的气象上下界。旧包遗漏该字段时，只读与 G 成品哈希、训练任务和数据集指纹相符的训练记录，不修改已发布包。无法核对时返回“训练范围不可核验”。

输入超出范围时保留计算结果及 `*_outside_training_range` 警告。2026-11-11 按用户要求，用户页面不再显示训练范围提示；接口、保存结果及适用范围校验继续保留。超出训练范围仍属于未经独立验证的外推，界面提示的调整不能替代跨季节验证。

实际验收使用已保存的 2026-11-09 和风天气响应：外温 −8.12℃，而当前 G 训练外温范围 24.2648～41.7761℃。该模型仍输出约 28.58℃ 的场均温，说明链路可计算，但当前模型不能据此声称适用于吉林冬季。正式使用需要覆盖目标季节、低温与相应棚内温度的训练/独立验证数据。

## 验证与复现

Java 回归覆盖账号权限、凭据归属/过期、幂等复用、预报修订、网格与配置修订、私有结果、历史加宽迁移、重启检查。前端覆盖地点切换、旧回执、失败重试、离页返回、来源匹配和既有布局。Python 覆盖 G/F 发布、推理与训练范围溯源。

选择性集成验收 `AutomaticWeatherAcceptanceTest` 默认跳过；显式开启 `tfield.automatic.acceptance=true` 并指定 `tfield.acceptance.root` 后，使用已保存的公开天气响应、本机已发布模型、隔离 H2 与 Python 实际推理。需先有 `.local/qweather-integration/live-query.json` 和测试中固定的示范包。这是本机验收，不应作为通用 CI 必跑项。

验收调用 `backend/scripts/verify_automatic_weather_field.py`，将 Java 构场请求、查询快照、24 点/37 切片结果、摘要、界面载荷、日志和验证报告放在 `.local/automatic-field/`。不新增收费天气请求，不向正式业务库写入测试结果，不读写用户密码。浏览器验证使用同一套真实计算载荷作隔离回放，不能称为正式账号在线业务验收。

本次结果：Java 83 项通过，另 1 项付费实时查询探针未开启；Python 35 项通过；前端相关 43 项通过，生产构建通过。无头浏览器验证选点自动构场、实际三维网格、训练范围提示、轮询不重复计算、页面刷新接续及 1440/1280/900 宽度无横向溢出，无页面脚本异常。此前完整前端测试中已知的旧回放控件断言等未在本次范围内修复，不能据此声称前端全库测试通过。

本机统一服务已部署此版本，Flyway 成功应用 V7，`/ops/health` 为 `ok`，未登录调用自动构场接口返回 401。默认部署指针已切换；正式账号的在线气象构场需要用户登录后选择地点触发。
