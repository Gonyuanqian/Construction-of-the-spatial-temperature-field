# 实时会话与播放操作协议 v1

适用版本：Java 业务服务 0.4.0 起、Python 内部实时协议 1。当前业务版本 0.5.0，仅支持单 Java、单 Python 实例与默认工作区。前端沿用现有实时工作台布局。

## 1. 数据归属与会话绑定

| 内容 | 负责方 | 保存位置 |
| --- | --- | --- |
| 当前实时会话 | Java | `workspace_context.live_session_id` |
| 模型、源清单、确认游标、运行状态 | Java | `live_session` |
| 操作编号、请求键、动作、确认状态 | Java | `live_operation` |
| 训练源与实时帧副本 | Python | `configs/live-sessions/<UUID>/train.xlsx`、`frames.xlsx` |
| 不可变清单、最近持久动作位置、去重回执 | Python | 同目录 `session.json` |
| 时钟、已接入帧与计算管线 | Python | 进程内，每个会话独立 |

Flyway V4 创建会话表、操作表及工作区引用，保留原模型和数据集记录。模型仍使用已有保存模型 ID，准备实时会话不登记新模型。

首次准备复制 `configs/live/train.xlsx` 与 `live/live.xlsx`，记录两份文件的 SHA-256、原 `signature`、相对存储键，以及模型包、成品和算法源码摘要。复制前后校验摘要，并检查训练段与帧段非空且帧段起点晚于训练段末尾。源生成与新会话准备必须串行；当前没有两文件整体发布的原子清单，不能将摘要复查当成并发生成场景的完整保护。

管线使用会话副本，并保留原签名判定语义。准备和帧查询都绑定会话模型，切换训练数据集或模型库当前项不会改动已有实时场。恢复时核对保存的清单与实际副本、模型字节和算法版本；不一致返回冲突，不把新默认源静默当作原源。已确认会话缺失时也不会以相同编号复制新默认源。

每次新会话成功后保留旧记录和文件。当前没有历史会话选择页面、归档检索或自动清理，需要团队制定保留策略后再加入。

## 2. 前端公开接口

原有 7 条实时方法与路径保留，Java 接管会话协调。`frame` 与 `volume` 仍由 Python 计算，Java 追加会话编号，不重算温度或改变空值。

| 接口 | 行为 |
| --- | --- |
| `GET /api/live/status` | 轻量读取会话时不拟合或追加帧；有待确认动作时先按同编号核对动作 |
| `POST /api/live/prepare` | 无会话时创建；有未完成准备时继续；已有会话时恢复原会话或返回已就绪 |
| `POST /api/live/sessions` | 使用当前默认源文件和所选模型创建新会话；旧会话必须暂停 |
| `POST /api/live/start?from_n=...` | 开始播放；可按旧契约显式选择起点 |
| `POST /api/live/pause` | 冻结在服务端当前位置 |
| `POST /api/live/next` | 前进一帧；保持原运行或暂停状态，末帧返回业务错误 |
| `GET /api/live/frame/{n}` | 返回可访问帧的断面和环境信息 |
| `GET /api/live/volume/{n}` | 返回可访问帧的三维体网格，保留原查询参数 |

准备仍为同步调用，兼容响应 `{state:"ready", seconds:数值}`，另增 `session_id`。首轮不引入异步准备任务接口，计算超时默认 600 秒。未知超时保留准备记录，后续状态核对或“继续准备”复用同一会话。明确失败的新准备不替换原工作区会话。

公开状态原字段保持：`state` 为 `idle` / `ready`，另有 `running`、`cursor`、`total`、`interval_s`。新增可选字段：

- `session_id`、`model_id`、`model_name`：当前生效的会话及其固定模型。
- `recovery_required`：原管线需要恢复。
- `preparing`：当前或候选会话正在准备。
- `pending_session_id`：候选会话还未切换生效。
- `detail`：准备、恢复或服务不可用的说明。
- `available:false`、`busy:true`：暂时不可核对，或协调器忙时返回已保存状态。

这些字段不保证每种状态均存在。失败或忙时的状态可能是最近记录，不应作为新的温度场结果。数据库内部状态 `preparing / ready / needs_restore / failed` 不直接替代原公开 `state`。

前端定期核对状态，只有会话、帧号或就绪状态变化才重取场；暂停也核对重启。新会话即使仍是第 0 帧也重新挂载三维模块，避免复用旧体数据。

## 3. 请求去重与旧页面防护

准备、重新准备、开始、暂停、下一帧支持 `Idempotency-Key`，格式为 1–128 个 ASCII 字母、数字、点、下划线、冒号或连字符，区分大小写。前端每次动作生成随机键，网络或 5xx 不确定响应后原页面重试继续使用原键；明确 4xx 后释放。键仅保留在当前页面内存中，关闭页面后通过状态查询和服务端候选会话继续恢复。

准备键标识一次新会话准备；已有会话的普通恢复按当前会话执行。操作键在会话内标识一次动作。Java 在调用 Python 前先登记 `pending` 操作，传递稳定的操作 UUID。Python 将动作后的游标与回执写入同一次原子文件替换；同 UUID 重复调用返回已保存回执，不重复推进。相同键更换动作或 `from_n` 返回 409。

响应丢失时 Java 继续核对同一编号；回执已保存则确认。若 Python 已重启且管线未恢复、没有该回执，则将未确认操作标记失败并提示恢复后重新操作。未知的网络或服务器错误保持待确认状态；不创建新的操作来盲目重试。当前会话只允许一个待确认播放操作。

同一次动作重试成功后，对前端返回最近确认状态，可能已经晚于原动作回执的帧号。去重保证动作不重复执行，不保证重复响应逐字一致。

前端所有变更请求附加 `X-TField-Expected-Session`：当前 UUID 或空会话的 `none`。查询帧和体网格附加 `session_id`。若当前会话已变化返回 409，防止旧页面控制新会话或把旧场当成新场。为兼容旧客户端，这些防护字段可省略；新客户端应提供。

## 4. 游标与恢复

播放间隔保持 300 秒；实时帧 `n` 映射到 `训练段长度 + n` 的计算时间索引。Python 读状态只根据服务端时钟计算游标，不生成温度场；Java 查询还会核对待确认动作，其中显式指定起点的 start 可能补接帧。场请求按序接入缺失帧，重复读同一帧不重复接入。

Java 约每 5 秒核对状态并持久化确认游标，播放动作确认和场查询也更新记录。Python 文件保存动作位置与回执，不在每个时钟推进时改写文件。自动播放中异常退出可能损失最后一次核对后的进度，恢复目标以 Java 确认游标为准，不假定能恢复到崩溃瞬间。

| 场景 | 处理 |
| --- | --- |
| Java 重启，Python 管线仍在 | 重读工作区与会话，再核对 Python，沿用原时钟 |
| Python 重启，文件和模型可用 | 仅加载登记资料，不在启动时构建；显示需要恢复 |
| 用户恢复原会话 | 验证原资料、重建原管线、顺序接入到确认帧；恢复后暂停 |
| 恢复耗时或断联 | 保留原记录与确认位置，继续准备或核对，不显示旧场为新结果 |
| 副本缺失、模型字节或算法版本变化 | 返回冲突；修复匹配资料或“重新准备”创建新会话 |
| 新会话准备失败 | 原会话仍是工作区当前项；候选失败记录和文件保留 |

Java 暂时不可核对 Python 时返回恢复说明，前端停止展示就绪场。Java 协调锁与训练工作区锁分开，慢构场不长时间占用模型读取所需的锁。当前锁和执行状态不支持多实例横向部署。

## 5. Python 内部协议

所有内部调用需要 `X-TField-Internal-Key`，前端不直接使用。前缀 `/internal/v1/live`：

| 方法与路径 | 请求 / 响应 |
| --- | --- |
| `GET /info` | `protocol_version:1` 与本次 Python 启动编号 |
| `GET /sources` | 默认帧源可用性、总帧数与间隔；不建管线 |
| `POST /sessions/{UUID}/prepare` | `{model_id, restore_cursor, expected_manifest?}`；返回 `{seconds,status}` |
| `GET /sessions/{UUID}` | 当前轻量状态、启动编号与固定清单 |
| `POST /sessions/{UUID}/operations` | `{operation_id,action,from_n}`；返回 `{operation_id,result,current}` |

`action` 为 `start / pause / next`。准备携带既有模型上下文头；帧计算还携带 `X-TField-Live-Session-Id`。Python 校验会话和模型一致，使用 ContextVar 将请求定位到该会话的私有管线。原 8503 无会话头入口仍属于旧单例，不继承 Java 会话状态，不应与 Java 日常操作混用。

## 6. 配置、备份与交接

新增 Python 配置 `TFIELD_LIVE_SESSION_ROOT`，默认 `backend/configs/live-sessions`，覆盖时必须为绝对路径。Java 通过相对存储清单登记，不直接加载这些文件。保留原数据库、内部凭据及 `TFIELD_BUSINESS_URL` 配置。

备份前暂停实时播放，等待准备及播放操作确认完毕，结束或取消训练，并暂停数据上传、模型保存及选择，确保数据库和文件处于同一业务时点。

`capture_migration_baseline.py --include-model-store` 备份模型、数据集、训练、实时会话、实时操作、工作区和 Flyway 历史；同时复制项目默认目录内的源副本、`session.json` 及训练结果。先向新空库导入 `model-store.sql`，再导入 `dataset-workspace-store.sql`，按相同 UUID 目录恢复文件；外置数据、训练、实时目录另行备份并恢复。凭据独立提供，不纳入业务备份。

恢复后 Python 不自动续播，用户恢复管线后暂停。旧版本回退也必须停止会话操作并保留新表与文件，旧单例不能承接这些会话对象。

阶段 4 已完成构建、V4 建表与首帧对照。阶段 5 在独立环境实际执行了重复步进、计算失联、非零确认帧恢复、真实 300 秒自动推进、新会话和空库恢复演练，原三维数值保持一致；训练、取消、跨重启保存也已联调。详见 [实际记录](../06-migration-acceptance-20261019.md)。所有响应丢失、断电及损坏资料窗口并未穷举；多实例和压力场景仍未覆盖。
